# Инвентаризация экранов

> Черновик v0 (2026-09-28). Раздел «Типичные провалы» пополняется из правок Влада.

## 1. Зачем

Закрывает боль «не все экраны учтены». В спеке пункты-фичи, API и экраны часто описывают одно и то же. При этом часть нужных экранов не описана вовсе, а на часть спека ссылается, но их нет.
На выходе — полный список экранов с приоритетом, в котором их будут делать. Каждый экран описан карточкой — это основа карты экранов.

## 2. Вход

- **Указатель спеки** (волна 0; если нет — собери минимальный сам) и **сама спека**.
- **Бриф** (`brief.md`): главный пользователь, ключевые потребности, роли, платформы.
- **`STATE.md` проекта → «Решения по проекту»** — решения Влада и заказчика, принятые позже брифа и модели. **Имеют приоритет** над брифом и моделью.
- **Модель** (`model.md`): объекты, статусы, матрица, **«действия без места»**, вычисляемые сущности.
  - В волне 1 модели ещё нет: делай черновой список только из спеки.
  - В волне 2 — добор по модели.

## 3. Границы

- **Не решаем**:
  - расположение и иерархию информации (это «Логика экрана»);
  - окончательную форму «экран / sheet / попап» (это скилл «Экран или попап»);
  - структуру навигации (это скилл «Навигация»).
- Как попасть / куда ведёт — пишем то, что есть в спеке или очевидно ([В]). Полностью это достраивает «Навигация».
- Бэкенд, CRM, как работают внешние сервисы — не наша забота.

## 4. Что искать (чек-лист)

- [ ] **Дедупликация:** пункты «фича / экран / API / компонент» про одно и то же → один экран. Фичи и API — источник фактов для карточки, а не экраны.
- [ ] **Экраны из спеки** — для каждой роли и платформы.
- [ ] **Сверка ссылок** — четыре разные проверки:
  - **явные ссылки:** каждое «ведёт на X», «переходит к X», «открывает X» → X есть в списке. Нет → экран с меткой [Д] «спека ссылается, экрана нет»;
  - **возможность без места:** роль «может» (писать, смотреть), а экрана для этого нет;
  - **безымянные экраны:** «один из 4 в таббаре», «вкладка X в навигации» — подразумеваются другие вкладки, но они не названы;
  - **обратные дыры:** экран есть, но на него не ведёт ни один путь.
- [ ] **Действия без места** из модели → экран-кандидат или часть существующего. Сначала **отсей** всё, что по `STATE.md` вне рамки (бэк-офис, CRM).
- [ ] **Неочевидные экраны** — пройти список 5.2.
- [ ] **Состояния** каждого экрана (правило 5.3).
- [ ] **Приоритет** каждого экрана: P1–P5 (правило 5.4).
- [ ] **Карточка** каждого экрана (формат в разделе 6).

## 5. Как решать

### 5.1 Что считать отдельным экраном
Отдельная запись — всё, что пользователь видит как отдельное «место»: экран, sheet, попап, панель. Форму окончательно решает следующий скилл; здесь пишем предварительно («экран?», «sheet?»).
**Не** отдельная запись:
- состояние экрана (загрузка, пусто) — оно идёт в поле «Состояния»;
- компонент внутри экрана (баннер, карточка) — он идёт в «Какую информацию даёт».

**Особые метки записей:**
- **Внешний узел** — не наш экран (платёжный шлюз, магазин приложений). Не рисуем и приоритета не даём, но на карте он нужен как узел для стрелок.
- **Кандидат на слияние с №N** — может оказаться секцией другого экрана. Пример: график клиента — секция карточки клиента. Запись оставляем, решает скилл «Экран или попап».
- **Условный** — нужен только при определённом ответе на вопрос. Пример: «OTP — если вход по телефону», «Обновите приложение — если нативное». Пиши: `[В] при условии: …`.
- **Общий для ролей** экран (список сделок у агента и админа) — **одна запись**, различия прав указать в карточке.
- **Системные экраны** — одна запись на обе платформы, если они не отличаются по смыслу.

### 5.2 Неочевидные экраны — пройти каждый пункт
Для каждого: нужен ли в этом продукте — да [В] / нет, потому что… / вопрос [Д].
- **Вход:** сплэш · вход / регистрация · OTP · восстановление доступа · выход.
- **Первый запуск:** онбординг · запрос разрешений (пуши, камера, геолокация — только те, что реально нужны продукту).
- **Профиль и настройки:** профиль · язык · настройки уведомлений · удаление аккаунта · юридические страницы (условия, конфиденциальность).
- **Коммуникация:** центр уведомлений · детали уведомления, если у него нет своего экрана-цели.
- **Поиск и фильтры:** «ничего не найдено».
- **Действия:** экран подтверждения (для денег, документов, необратимого) · экран результата (успех / неудача), если нужен по правилу 5.3.
- **Системные:** нет сети · пуш или ссылка ведёт на удалённый контент · «обновите приложение» · общая ошибка.
- **Внешние переходы:** уход во внешний сервис (оплата) и возврат из него.
- **Для каждой второстепенной роли:** её вход и главный экран.

Системные экраны Влад часто не успевал рисовать. Команда их **не пропускает**, но делает последними (P5).

### 5.3 Состояния — по умолчанию
Для каждого экрана перечисли, какие нужны:
- **загрузка** — скелетон;
- **пусто** — если на экране список или данные, которых может не быть (0 из «0 / 1 / много» в модели);
- **ошибка** загрузки;
- **ввод с ошибкой валидации** — если на экране есть ввод;
- **успех** — **только если без него результат непонятен.** Нужен после отправки, оплаты, сохранения без перехода. **Не нужен**, если результат и так виден: после входа открылось приложение — сообщение «вы вошли» не нужно;
- **доменные состояния** из статусов модели: например, объект «строится / готов», этап «оплачен / просрочен».

Состояния **рисуются после утверждения основного экрана**. Здесь их только перечисляем.

### 5.4 Приоритет — в каком порядке делаем
Так работает Влад: сначала главное, потом по значимости.

| Приоритет | Что | Почему |
|---|---|---|
| **P1 — якорь** | Главный экран главного пользователя. По умолчанию **один**; второй — только если Влад попросит | Утверждается первым и задаёт стиль для всего остального |
| **P2 — вход** | Сплэш, вход / регистрация / OTP / восстановление, онбординг | Следующее после якоря |
| **P3 — основные** | Экраны ключевых потребностей главного пользователя | Ради них продукт |
| **P4 — второстепенные роли** | Основные экраны агента, админа и т.п. | Сначала только основные, без состояний |
| **P5 — системные и служебные** | Профиль и настройки, разрешения, нет сети, «обновите приложение», удалённый контент, юридические, выход, удаление аккаунта | Нужны, но в конце |

Состояния любого экрана — после утверждения самого экрана.

### 5.5 Как попасть / куда ведёт
Берём из спеки (`[С п.N]`) и из очевидной логики (`[В]`). Пуш — тоже вход.
**Экран, в который нельзя попасть, — это [Д].** Экран, из которого некуда уйти, — тоже.

## 6. Формат выхода — `inventory.md`

```
# Инвентаризация: <продукт>

## Сводка
| # | Экран | Роль · платформа | Форма (предв.) | Приоритет | Источник |
(источник: [С п.N] / [В] неочевидный / [Д] спека ссылается, экрана нет)

## Карточки
### <#>. <Название на языке спеки> — <по-русски>
- Роль · платформа: …
- Форма (предв.): экран / sheet? / попап?
- Приоритет: P1–P5
- Что за экран: 1–2 строки — зачем он пользователю
- Какую информацию даёт: список без порядка важности
- Как попасть: … [С|В]
- Куда ведёт: → … [С|В]
- Состояния: загрузка · пусто · ошибка · … (доменные)
- Из спеки: п. …

## Дедупликация
| Пункты спеки | → Экран |

## Сверка ссылок
| Вид (явная / без места / безымянный / обратная дыра) | Где в спеке | Что | Решение |

## Добор по модели (действия без места)
| Действие | Решение: экран №N / часть №N / вне рамки (почему) |

## Неочевидные экраны
| Пункт списка 5.2 | Нужен? | Почему |

## Дыры → вопросы Владу (только меняющие набор экранов)
```

Карточки — основа **карты экранов** в FigJam: там карточка — это блок, а «куда ведёт» — стрелки. Карту рисуют после скилла «Навигация».


## Правило «сначала реши сам» (Влад, 29.09)

Прежде чем выносить вопрос Владу — **реши сам, как сеньор-дизайнер**:
1. Сформулируй 2–3 варианта.
2. Выбери один с обоснованием: логика продукта + аудитория + 1–2 рефа из Mobbin (с разбором «почему так»).
3. Запиши как решение с меткой [В] и строкой «почему».

Вопросом Владу выносится только:
- **бизнес-факт**, который нельзя вывести (что продаёт компания, какие правила у заказчика);
- **развилка вкуса или стратегии**, где оба варианта равноценны.

Даже тогда — с твоей рекомендацией.

**Mobbin:** коннектор claude.ai. Загрузка: ToolSearch с запросом select:mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_screens,mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_flows. Сообщения «mobbin requires authentication» относятся к дублю-плагину — игнорировать их и пользоваться коннектором.

## 7. Типичные провалы

- Фича и экран из спеки посчитаны как два экрана.
- Спека ссылается на экран, которого нет, — не замечено.
- Экран без входа («как попасть» пусто) или без выхода.
- Состояние («пусто», «загрузка») записано отдельным экраном.
- Пропущены системные экраны — или, наоборот, им дан высокий приоритет.
- «Успех» добавлен там, где результат и так виден (после входа).
- Второстепенные роли расписаны со всеми состояниями раньше, чем готовы основные экраны главного пользователя.
- В «какую информацию даёт» уже расставлен порядок и лейаут — это работа следующего этапа.
