# Инвентаризация экранов

> v1 (2026-10-23) — коротко; история — `log.md`. Приоритеты — **Пр1–Пр5** (не путать с принципами P1–P20 из `shared-ux-principles`).

## 1. Вход и границы
Указатель спеки (нет → минимальный сам) · спека · `brief.md` (главный пользователь, потребности, роли, платформы) · `model.md` (объекты, статусы, матрица, «действия без места», вычисляемые; в волне 1 модели нет — список только из спеки) · STATE. Решения — `shared-runtime` §2; Mobbin — §3.
Не решаем: иерархию информации (`spec-screen-logic`), окончательную форму (`spec-screen-form`), навигацию (`spec-navigation`). «Как попасть / куда ведёт» — из спеки или очевидное [В]. Бэкенд, CRM, внешние сервисы — не наша забота.

## 2. Что сделать
- [ ] **Дедупликация:** пункты «фича / экран / API / компонент» про одно и то же → один экран; фичи и API — факты для карточки. **Проверка:** ни один пункт спеки не дал двух экранов с одним содержанием.
- [ ] **Экраны из спеки** — на каждую роль и платформу.
- [ ] **Сверка ссылок** — четыре проверки: явные («ведёт на X» → X в списке; нет → экран [Д] «спека ссылается, экрана нет») · возможность без места (роль «может», экрана нет) · безымянные («один из 4 в таббаре» → остальные вкладки) · обратные дыры (экран есть, пути нет).
- [ ] **Действия без места** из модели → экран-кандидат или часть существующего; сначала отсеять всё, что по STATE вне рамки.
- [ ] **Неочевидные экраны** — список §3, на каждый: да [В] / нет, потому что… / [Д].
- [ ] **Состояния** каждого экрана (§4). **Приоритет** Пр1–Пр5 (§5). **Карточка** (§7). **Проверка:** «Как попасть» и «Куда ведёт» непусты; пусто → [Д].

Отдельная запись — всё, что пользователь видит как отдельное «место»: экран, sheet, попап, панель (форма предварительная: «экран?», «sheet?»). **Не** запись: состояние (→ «Состояния»), компонент внутри экрана (→ «Какую информацию даёт»).
Метки: **Внешний узел** (шлюз, магазин приложений — не рисуем, приоритета нет, на карте нужен) · **Кандидат на слияние с №N** (решает `spec-screen-form`) · **Условный** — `[В] при условии: …` · **Общий для ролей** — одна запись, права в карточке · **Системные** — одна запись на обе платформы, если смысл один.

## 3. Неочевидные экраны (пройти каждый)
Вход: сплэш · вход / регистрация · OTP · восстановление · выход. Первый запуск: онбординг · разрешения (только нужные продукту). Профиль: профиль · язык · уведомления · удаление аккаунта · юридические. Коммуникация: центр уведомлений · детали уведомления без своего экрана-цели. Поиск: «ничего не найдено». Действия: подтверждение (деньги, документы, необратимое) · результат (по §4). Системные: нет сети · удалённый контент · «обновите приложение» · общая ошибка. Внешние переходы: уход и возврат. Каждая второстепенная роль: вход и главный экран. Системные не пропускать — делать последними (Пр5).

## 4. Состояния — по умолчанию
Загрузка (скелетон) · пусто (если есть список или данные с «0» в модели) · ошибка загрузки · ввод с ошибкой (если есть ввод) · **успех — только если без него результат непонятен** (после отправки, оплаты, сохранения без перехода; после входа открылось приложение — не нужен) · доменные из статусов модели. Рисуются после утверждения основного экрана; здесь перечислить.

## 5. Приоритет — порядок работы

| Приоритет | Что | Почему |
|---|---|---|
| **Пр1 — якорь** | Главный экран главного пользователя; по умолчанию **один**, второй — только по просьбе Влада | Утверждается первым, задаёт стиль |
| **Пр2 — вход** | Сплэш, вход / регистрация / OTP / восстановление, онбординг | После якоря |
| **Пр3 — основные** | Экраны ключевых потребностей главного пользователя | Ради них продукт |
| **Пр4 — второстепенные роли** | Основные экраны агента, админа — без состояний | После главного пользователя |
| **Пр5 — системные и служебные** | Профиль, настройки, разрешения, нет сети, «обновите», удалённый контент, юридические, выход, удаление аккаунта | Нужны, но в конце |

Состояния — после утверждения самого экрана. **Проверка:** Пр1 ровно один; у Пр4 нет состояний раньше, чем утверждены Пр3.

## 6. Как попасть / куда ведёт
Из спеки (`[С п.N]`) и очевидной логики (`[В]`); пуш — тоже вход. Экран без входа или без выхода — [Д].

## 7. Формат выхода — `inventory.md`

```
# Инвентаризация: <продукт>

## Сводка
| # | Экран | Роль · платформа | Форма (предв.) | Приоритет | Источник |
(источник: [С п.N] / [В] неочевидный / [Д] спека ссылается, экрана нет)

## Карточки
### <#>. <Название на языке спеки> — <по-русски>
- Роль · платформа: …
- Форма (предв.): экран / sheet? / попап?
- Приоритет: Пр1–Пр5
- Что за экран: 1–2 строки — зачем он пользователю
- Какую информацию даёт: список без порядка важности
- Как попасть: … [С|В]
- Куда ведёт: → … [С|В]
- Состояния: загрузка · пусто · ошибка · … (доменные)
- Из спеки: п. …

## Дедупликация
| Пункты спеки | → Экран |
## Сверка ссылок
| Вид (явная / без места / безымянный / обратная дыра) | Где в спеке | Что | Решение |
## Добор по модели (действия без места)
| Действие | Решение: экран №N / часть №N / вне рамки (почему) |
## Неочевидные экраны
| Пункт §3 | Нужен? | Почему |
## Дыры → вопросы Владу (только меняющие набор экранов)
```

Карточки — основа карты экранов в FigJam (`shared-figjam-map`): карточка — блок, «куда ведёт» — стрелки. Карту рисуют после `spec-navigation`.
