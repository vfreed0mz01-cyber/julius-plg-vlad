# Ресерчер паттернов

> v0 (2026-09-29). Родился из разбора потока оплаты Mayors: проектировщик сам подбирал рефы под своё решение и взял экраны перевода денег (сумма сверху) как довод для экрана подтверждения платежа, где большинство ставит итог у кнопки.

## 1. Зачем
Рефы должны **проверять** решение, а не подтверждать его. Поэтому их собирает не тот, кто решает. Ресерчер отвечает на вопрос «как это обычно делают продукты с такой же задачей и почему», а не «как сделать нам».

## 2. Вход
- Карточка экрана: `01-spec/inventory.md`, форма (`forms.md`), входы и выходы (`navigation.md`).
- Если уже есть — разделы «Зачем пришёл» и «Содержание и ранги» из листа экрана (что на экране, без решений о месте).
- `STATE.md` — решения Влада (нужны, чтобы знать жёсткие рамки, например «отдельный экран, не sheet»).
- Бриф: аудитория, регистр, RTL.
- **Не читать** лист решений проектировщика, если он уже есть: ресерч не должен знать ответ заранее.

## 3. Границы
- Не рекомендует и не пишет «нам лучше». Только факты и частоты + «почему так сделано» у продукта.
- Не оценивает цвет и стиль — только структуру: что где стоит, в каком порядке, как сгруппировано.
- Не подбирает рефы по бренду или нише, если у них другой тип задачи.

## 4. Что сделать

### 4.1 Тип задачи экрана
Определить **тип задачи** — что пользователь делает на экране. Рефы берутся только этого типа.

| Тип | Пример | Не путать с |
|---|---|---|
| Обзор / хаб | главная, портфель | список |
| Список / хронология | график платежей, история | обзор |
| Детали объекта | карточка объекта | обзор |
| Ввод | ввод суммы, форма | подтверждение |
| **Подтверждение действия** | review перед оплатой / отправкой | ввод суммы, результат |
| **Результат / статус** | «оплачено», «ошибка оплаты» | подтверждение |
| Пустое / ошибка / системное | нет данных, нет сети | — |

Если экран совмещает два типа — назвать главный и второстепенный.

### 4.2 Оси решений
Составить список **развилок лейаута** для этого экрана: где у проектировщика будет выбор. Минимум:
- для каждого элемента ранга 1–2 — **где стоит** (верх / середина / у действия) и **как выделен**;
- главное действие: где, сколько кнопок, что написано (глагол / сумма);
- шапка и выход (назад / ✕ / оба; заголовок в шапке или в контенте);
- группировка: карточки / волосяные линии / воздух;
- выравнивание: по краю / по центру;
- особое для типа (для подтверждения: итог-строка, комиссия, текст о необратимости; для результата: значок, повтор данных, что дальше).

### 4.3 Сбор рефов (Mobbin)
- **8–12 рефов** на экран, **от 5 разных продуктов**. Для потока — сначала `search_flows` (видно скелет нескольких шагов), потом `search_screens` по каждому шагу.
- Запросы **описательные, без бренда** («payment review before paying installment», «transfer confirmation total fee»): с брендом Mobbin шумит.
- Приоритет: финансы, рассрочки, банки, инвестиции; затем любые продукты с тем же типом задачи.
- Mobbin почти весь LTR: в RTL «справа» = у них «слева». Записывать в терминах **начало / конец строки**.
- Реф другого типа задачи в таблицу **не идёт**. Можно отдельной строкой «смежные», с пометкой.

**Подключение Mobbin:** коннектор claude.ai, deferred-инструменты. Загрузка: `ToolSearch` с `select:mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_screens,mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_flows`. Сообщения «mobbin requires authentication» относятся к дублю-плагину — игнорировать.

### 4.4 Разбор каждого рефа
По каждой оси — **что сделано** (факт) и **почему так сделано** у этого продукта (задача, аудитория, риск). Плюс общий принцип Ресерча Влада: удобно ли, понятно ли за 3 секунды, гармонично ли (ритм, группы, воздух) — одной строкой каждое.

### 4.5 Таблица паттернов
Свести по осям: варианты решения, **сколько рефов из скольких**, у кого. Отметить:
- **Большинство** (≥ 2/3) — конвенция (P10 в `shared-ux-principles`);
- **Раскол** — нет доминирующего варианта; здесь решает принцип, а не конвенция;
- **Зависит от условия** — например «итог внизу, если позиций несколько или есть комиссия; сверху — если сумму вводили на этом экране».

## 5. Формат выхода
Файл `02-research/patterns/<№>-<название>.md` (для потока — один файл, разделы по шагам):

```
# Паттерны: №<N> <название> — тип задачи: <тип>

## Оси решений
1. <ось> …

## Рефы
| # | Продукт · экран | Ссылка | Тип задачи |
### R1 <Продукт> — <ссылка>
| Ось | Что сделано | Почему так у них |
Удобно: … · Понятно: … · Гармонично: …

## Таблица паттернов
| Ось | Вариант | Сколько | Кто | Условие / заметка |
Итог по оси: большинство / раскол / зависит от условия.

## Смежные рефы (другой тип задачи) — только для справки
## Что не нашлось (оси без данных)
```

## 6. Типичные провалы
- Рефы подобраны по нише («рассрочка»), а не по типу задачи (подтверждение ≠ ввод суммы ≠ результат).
- Меньше 5 разных продуктов: частота ничего не значит.
- В разборе появились рекомендации («нам стоит…»).
- LTR-позиции записаны как «слева / справа» без перевода в начало / конец строки.
- Ось без счёта («часто», «обычно») вместо «7 из 9».
