# Модель продукта

> v1 (2026-10-23) — коротко; история и уроки — `log.md`. Правило = действие + как проверить.

## 1. Вход и границы
Указатель спеки (нет → собрать минимальный сам) · спека целиком · `brief.md` (роли, главный пользователь, потребности, строка «чувство · механика · данные»; брифа нет → роли из спеки) · STATE. Решения — `shared-runtime` §2; Mobbin — §3.
Не наша забота: как данные попадают в систему (CRM, импорт) — одна строка [В] «данные приходят извне»; как работает внешний сервис — нужны только видимые состояния («оплачено / в обработке / не прошло»); API, БД, стек. Глубина — по главному пользователю; второстепенные роли — без раздувания.

## 2. Что найти
- [ ] **Объекты**, включая неявные: уведомление, сообщение, задача, документ, профиль, вход. Источники: существительные в заголовках экранов и критериях приёмки; «список X» / «экран X» → объект X; «статус …» → поле-статус; уведомление или событие → объект «уведомление» + событие-источник; «сумма / прогноз / просрочка» → поле или вычисляемый статус; у него свой список или навигация → **вычисляемая сущность** (отдельная таблица).
- [ ] **Синонимы**: два названия одного объекта или один — двух; спека не даёт ответа → описать оба варианта, [Д]. Разные наборы статусов одного объекта в разных пунктах → один набор [В], исходные — в «Синонимы».
- [ ] **На объект**: поля · **поле-«имя»** (как пользователь назовёт вслух: «квартира 12 в проекте X», не ID — будущий заголовок карточки) · **поле-статус** · связи (чей, 1:1 / 1:N). Разметка только имя / статус / остальное; ранги 1-2-3 — `spec-screen-logic`.
- [ ] **Реальный контент** ключевых полей: типичное · максимум (самое длинное, на иврите) · пусто · 0 / 1 / много. **Проверка:** ни одного латинского плейсхолдера; у каждого списка есть «0».
- [ ] **Данные под механику**: каждое поле из строки «чувство · механика · данные» брифа есть в модели; нет → поле [В] + вопрос заказчику в «Дыры».
- [ ] **Жизненный цикл** объектов со статусом: статус → как попадает → куда переходит; финальные / отменённые / **вычисляемые (по времени)** помечены. **Проверка:** у каждого статуса есть представление в интерфейсе, иначе [Д]; переход, важный главному пользователю, без уведомления → [Д]. Объект без статусов в спеке — минимальный цикл [В] только если без него нельзя нарисовать состояния экрана (возврат из оплаты: в обработке / оплачено / не прошло); иначе не выдумывать.
- [ ] **Матрица «роль × объект × действие»**: базовые (создать · смотреть · изменить · удалить · найти / фильтровать) + доменные (оплатить, подтвердить, отправить). Клетка: ✅ `[С п.N]` · ✅⚠️ есть в спеке, но нет пути · ⚠️ `[Д]` нужно, в спеке нет · ➖ `[В] причина`. Сжимать: строка-умолчание на роль («Инвестор: создать / изменить / удалить ➖ [В] — данные извне, кроме: …»), гость одной строкой, создать / изменить / удалить — одна клетка. Действия без экрана → «действие без места» → инвентаризация; экраны здесь не перечислять.
- [ ] **Ограничения**, видимые пользователю: кто видит только своё · какие события вызывают уведомления · внешние переходы (оплата).
- [ ] **Трассировка**: каждая боль и цель бизнеса из брифа → объект + действие → [С] есть / [Д] нет. До экрана не доводить — это критик после инвентаризации.

## 3. Дыры
Сначала восстановить, как бизнес работает вне приложения, и записать [В] («сделку оформляют офлайн, объект присваивает сотрудник в CRM, приложение отражает»). [Д] — только то, что меняет набор экранов или то, что видит пользователь; одна дыра — одной общей строкой. **Проверка:** ни один [Д] не про CRM / API / подтверждение оплаты; ни один [Д] не повторён у нескольких объектов.

## 4. Формат выхода — `model.md`
Метки [С] / [В] / [Д]; в таблицах — в каждой ячейке.

```
# Модель: <продукт>

## Общие допущения
- Откуда данные: … [В]
- Главный пользователь: …

## Объекты
| Объект | Что это (1 строка) | Поле-«имя» | Поле-статус | Связи |

## Поля и реальный контент
### <Объект>
| Поле | Разметка (имя/статус/—) | Типичное | Максимум | Пусто | 0/1/много | Формат |

## Вычисляемые сущности
| Сущность | Из чего считается | Где живёт (список / число / экран) | Кто видит |

## Жизненные циклы
### <Объект>
| Статус | Как попадает | Куда переходит | Виден кому | Уведомление? |
+ блок mermaid (см. ниже)

## Матрица «роль × объект × действие»
(строки-умолчания на роль + таблица исключений)

## Ограничения (видимые пользователю)
## Трассировка болей и целей
| Боль / цель | Объект + действие | Есть? |
## Действия без места (→ инвентаризация)
## Синонимы и неясности
## Дыры → вопросы Владу (только меняющие экраны)
```

### Шаблон mermaid (совместим с FigJam)

```
stateDiagram-v2
    state "פתוח" as open
    state "שולם" as paid
    state "חרג ממועדו (вычисляемый)" as overdue
    [*] --> open : этап открылся
    open --> overdue : дата прошла
    open --> paid : оплата подтверждена
    paid --> [*]
```

Ивритские и русские названия — только через `state "…" as id`; в подписях переходов нет двоеточий и квадратных скобок (парсер FigJam падает); `classDef` не использовать; дыры — словом «ДЫРА» в названии, вычисляемые — «(вычисляемый)».
