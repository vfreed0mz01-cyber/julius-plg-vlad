# Модель продукта

> v0.2 (2026-09-28): правки после прогона на Mayors и замечаний Влада.
> Раздел «Типичные провалы» пополняется из правок Влада.

## 1. Зачем

Модель — фундамент, на котором стоят экраны:
- **Объект** почти всегда превращается в экраны: список, карточка в списке, детали.
- **Поля** — содержимое этих экранов.
- **Статусы** — состояния экранов.
- **Матрица** «роль × объект × действие» ловит забытые экраны.

Какие боли закрывает:
- «не все экраны учтены»;
- забытые состояния;
- дизайн на «Lorem ipsum», который ломается на реальных данных (иврит рвётся посреди слов).

## 2. Вход

- **STATE.md проекта → «Решения по проекту»** — решения Влада и заказчика, принятые позже. Имеют приоритет над спекой и предыдущими артефактами.
- **Указатель спеки (волна 0).** Если его нет — собери минимальный сам (номер пункта → тип → суть).
- **Сама спека** — целиком.
- **Бриф из «Рамки продукта»**, если уже готов: роли, **главный пользователь**, потребности. Если брифа ещё нет — роли берутся прямо из спеки.

## 3. Границы — что НЕ наша забота

Мы дизайнеры. Нас интересует то, что пользователь **видит и делает**. Не разбираем и не выносим вопросами:
- **Как данные попадают в систему** (CRM, бэк-офис, импорт), если спека не делает это частью продукта. Пример: объект «присваивают» инвестору в CRM — достаточно одной строки [В] «данные приходят извне».
- **Как работает внешний сервис** (платёжный шлюз, push-сервис): как и почему подтверждается оплата — не наш вопрос. Нам нужны только **видимые состояния**: «оплачено», «в обработке», «не прошло».
- **API, БД, стек.**

**Приоритет ролей.** Глубина проработки — по главному пользователю из брифа. Второстепенные роли (агент, админ) — проще, без раздувания.

## 4. Что искать (чек-лист)

- [ ] **Объекты** — все «вещи» продукта, включая неявные: уведомление, сообщение, задача, документ, профиль, вход.
- [ ] **Синонимы** — один объект под разными названиями (или два разных под одним). Сюда же — **разные наборы статусов** одного объекта в разных пунктах спеки.
- [ ] **Для каждого объекта:**
  - [ ] поля;
  - [ ] **поле-«имя»** — по чему пользователь узнаёт объект;
  - [ ] **поле-статус**;
  - [ ] связи: чей объект, 1:1 или 1:N.
- [ ] **Реальный контент** ключевых полей: типичное · максимум / самое длинное · пусто · количество (0 / 1 / много).
- [ ] **Вычисляемые сущности** — то, что считается, но живёт как отдельный список или экран (просрочки, сводка портфеля, прогнозы).
- [ ] **Жизненный цикл** объектов со статусами: статус → как попадает → куда переходит. Отдельно: финальные / отменённые / **вычисляемые** (по времени).
- [ ] **Матрица «роль × объект × действие»:**
  - базовые действия: создать · смотреть · изменить · удалить · найти / фильтровать;
  - доменные действия: оплатить, подтвердить, отправить…
- [ ] **Ограничения**, видимые пользователю:
  - права: кто видит только своё;
  - **уведомления** — какие события их вызывают;
  - внешние переходы (оплата).
- [ ] **Трассировка:** каждая **боль** и каждая **цель бизнеса** из брифа → объект + действие.

## 5. Как решать

### 5.1 Как находить объекты
- Существительные в спеке, особенно в заголовках экранов и в критериях приёмки.
- Каждый «список X» / «экран X» → объект X.
- Каждое «статус …» → поле-статус.
- Каждое уведомление или событие → объект «уведомление» + событие-источник.
- Каждое вычисление («сумма», «прогноз», «просрочка») → поле или вычисляемый статус. Если у него есть свой список или навигация — это **вычисляемая сущность** (отдельная таблица).

### 5.1а Данные под механику (✓ Влад 07.10, урок Tenderflow: 20 вариантов за 6 дней до P)
Строка «чувство · механика · данные» из брифа — проверить, что каждое нужное поле есть в модели (у Tenderflow сумма тендера «אומדן» появилась только после правок заказчика, и механика «счёт упущенного» до этого была невозможна). Нет поля → объект / поле [В] + вопрос заказчику в «Дыры».

### 5.2 Сначала восстанови процесс, потом ставь дыру
Прежде чем ставить [Д], восстанови, как бизнес работает **вне приложения**, и запиши как [В]. Пример: «сделку оформляют офлайн, объект присваивает сотрудник в CRM, приложение отражает».
**Вопросом Владу** выносится только то, что **меняет набор экранов или то, что видит пользователь**.
Не повторяй одну и ту же дыру у каждого объекта — вынеси её **одной общей строкой**.

### 5.3 Синонимы
Если два названия могут означать одно и то же, а спека не даёт ответа — опиши оба варианта (одно и то же / разные со связью). Это [Д].
Разные наборы статусов одного объекта: в жизненном цикле объедини их в один набор с меткой [В], исходные варианты перечисли в «Синонимах».

### 5.4 Поле-«имя»
Как пользователь назвал бы объект вслух: «квартира 12 в проекте X», а не ID. Это будущий заголовок карточки.
Полную иерархию полей (ранги 1-2-3) **здесь не делать** — это «Логика экрана». Здесь только разметка: **имя / статус / остальное**.

### 5.5 Реальный контент
- Для иврита — реалистичные длинные значения, а не короткие латинские заглушки.
- Для списков — 0 / 1 / много: отсюда будущие пустые состояния.

### 5.6 Жизненный цикл
- **Каждый статус должен где-то отображаться.** Нет представления — [Д].
- **Вычисляемые статусы** (по времени) помечай отдельно.
- Для каждого перехода, важного для **главного пользователя**: нужно ли уведомление? Нужно, а нет — [Д].
- **Объект без статусов в спеке:** предлагай минимальный цикл [В] **только если без него нельзя нарисовать состояния экрана**. Пример: возврат из внешней оплаты требует «в обработке / оплачено / не прошло». Иначе — не выдумывай.

### 5.7 Матрица — компактно
В клетке одно из значений:
- ✅ `[С п.N]` — есть в спеке;
- ✅⚠️ — есть в спеке, но **нет пути** (роль «может», а попасть неоткуда);
- ⚠️ `[Д]` — по логике нужно, в спеке нет;
- ➖ `[В] причина` — не нужно.

**Как сжимать:**
- строка-умолчание на роль: «Инвестор: создать / изменить / удалить ➖ [В] — данные приходят извне, кроме: …»;
- гость — одной строкой;
- создать / изменить / удалить можно группировать в одну клетку.

Действия, которые матрица нашла, но у которых нет экрана, называй **«действие без места»** и передавай в инвентаризацию. Сами экраны здесь не перечисляй.

### 5.8 Трассировка
`боль или цель → объект + действие → [С] есть / [Д] нет`.
До экрана трассировку здесь не доводим. Её доводит критик после инвентаризации.

## 6. Формат выхода — `model.md`

Метки [С] / [В] / [Д]; в таблицах — в каждой ячейке.

```
# Модель: <продукт>

## Общие допущения
- Откуда данные: … [В]
- Главный пользователь: …

## Объекты
| Объект | Что это (1 строка) | Поле-«имя» | Поле-статус | Связи |

## Поля и реальный контент
### <Объект>
| Поле | Разметка (имя/статус/—) | Типичное | Максимум | Пусто | 0/1/много | Формат |

## Вычисляемые сущности
| Сущность | Из чего считается | Где живёт (список / число / экран) | Кто видит |

## Жизненные циклы
### <Объект>
| Статус | Как попадает | Куда переходит | Виден кому | Уведомление? |
+ блок mermaid (см. ниже)

## Матрица «роль × объект × действие»
(строки-умолчания на роль + таблица исключений)

## Ограничения (видимые пользователю)
## Трассировка болей и целей
| Боль / цель | Объект + действие | Есть? |
## Действия без места (→ инвентаризация)
## Синонимы и неясности
## Дыры → вопросы Владу (только меняющие экраны)
```

### Шаблон mermaid (совместим с FigJam)

```
stateDiagram-v2
    state "פתוח" as open
    state "שולם" as paid
    state "חרג ממועדו (вычисляемый)" as overdue
    [*] --> open : этап открылся
    open --> overdue : дата прошла
    open --> paid : оплата подтверждена
    paid --> [*]
```

Правила:
- ивритские и русские названия — только через `state "…" as id`;
- **в подписях переходов нет двоеточий и квадратных скобок** — парсер FigJam на них падает;
- `classDef` не использовать;
- дыры помечать словом «ДЫРА» в названии, вычисляемые — «(вычисляемый)».


## Правило «сначала реши сам» (Влад, 29.09)

Прежде чем выносить вопрос Владу — **реши сам, как сеньор-дизайнер**:
1. Сформулируй 2–3 варианта.
2. Выбери один с обоснованием: логика продукта + аудитория + 1–2 рефа из Mobbin (с разбором «почему так»).
3. Запиши как решение с меткой [В] и строкой «почему».

Вопросом Владу выносится только:
- **бизнес-факт**, который нельзя вывести (что продаёт компания, какие правила у заказчика);
- **развилка вкуса или стратегии**, где оба варианта равноценны.

Даже тогда — с твоей рекомендацией.

**Mobbin:** коннектор claude.ai. Загрузка: ToolSearch с запросом select:mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_screens,mcp__ec6844fa-4e4c-4e4e-a903-2ff1b8a0e4a2__search_flows. Сообщения «mobbin requires authentication» относятся к дублю-плагину — игнорировать их и пользоваться коннектором.

## 7. Типичные провалы

- Забыт неявный объект: уведомление, сообщение, задача, профиль, вход.
- Два названия одного объекта превратились в два объекта (или наоборот) без вопроса.
- У статуса нет представления в интерфейсе.
- «Просрочено» и другие вычисляемые статусы не учтены.
- Реальный контент не описан → дизайн на «Lorem ipsum».
- Переход статуса важен для главного пользователя, но уведомления нет.
- **Ушёл в бэкенд:** вопросы про CRM, API, как подтверждается оплата — не наша забота (правило Влада).
- **Одна дыра повторена в каждой клетке** вместо одной общей строки.
- **Второстепенные роли проработаны так же глубоко, как главный пользователь** → раздутая модель.
- Выдуман жизненный цикл, который не нужен ни одному экрану.
