# Навигация

> v1 (2026-10-23) — коротко; история — `log.md`.

## 1. Вход и границы
`inventory.md` (экраны, приоритеты, черновые входы / выходы) · `forms.md` (формы, слияния, закрытие) · `model.md` (события, «Уведомление?») · `brief.md` (главный пользователь, главное действие, точка входа, платформы, аудитория) · `niche.md` (лучший конкурент для «было → стало») · STATE. Решения — `shared-runtime` §2; Mobbin — §3.
Флоу ключевых потребностей — здесь (§4). Содержание экранов не решаем.

## 2. Что сделать
- [ ] **Структура** на роль и платформу: таббар (мобайл) / боковое меню (веб), разделы, что в каждом.
- [ ] **Место** каждого экрана: раздел + уровень (1 — вкладка / пункт меню, 2, 3…).
- [ ] **Входы и выходы** каждого экрана — финально (черновые из инвентаризации проверить и дополнить).
- [ ] **«Назад»** для каждого экрана.
- [ ] **Пуши**: на каждое событие модели с «Уведомление? — да» и из решений проекта — суть текста → экран-цель (где сразу понятно, что делать) → «назад» (§3) · цель удалена → «контент не найден».
- [ ] **Шапка**: заголовок, «назад», глобальные иконки (уведомления, чат), бейджи — по уровням; глобальные иконки только на уровне 1, если STATE не говорит иное.
- [ ] **Вход в продукт**: после входа · повторный запуск · из пуша при закрытом приложении.
- [ ] **Флоу** каждой ключевой потребности (§4).
- [ ] **Проверки**: ни одного экрана без входа · ни одного тупика · главное действие главного пользователя ≤ 2 тапов от точки входа · «было → стало» записано.

## 3. Правила
**Мобайл**
- Таббар ≤ 5 вкладок; подписи у вкладок всегда; вкладка = раздел, в который ходят часто. **Проверка:** у каждой вкладки есть потребность из брифа или частота «часто» в контексте роли.
- Глубина от вкладки ≤ 3 уровней для основных разделов и путей к главным действиям. Осознанное углубление «подробнее о…» — допустимо и на 4-м.
- «Назад» всегда есть и ведёт туда, откуда пришёл; из пуша — на главную (или на родителя в разделе, если понятнее). **Проверка:** ни одно «назад» не ведёт из приложения.
- RTL: стрелка «назад» смотрит вправо; порядок вкладок справа налево — первая (главная) справа.
- Не уровень: модальный поток (подтверждение → шлюз → результат), sheet, панели, диалоги, полноэкранный просмотр; глобальные экраны (чат, центр уведомлений) открываются поверх из любой глубины.
- Действие ≠ раздел: «Новый X» — кнопка в разделе, не пункт меню; пункт меню — раздел со списком («Апдейты» = история + кнопка «Новый апдейт»).

**Веб (рабочие роли)**
- Боковое меню с подписями; в RTL — справа. Детали из списка — боковая панель (`forms.md`), сложное — страница. После входа — главная своей роли.

## 4. Флоу ключевых потребностей
На каждую потребность главного пользователя из брифа (+ 1–2 главные задачи каждой второстепенной роли):
- **Вход** (пуш, иконка, главная) · **шаги** (экран → действие → экран…, что видит и что делает) · **клики** — сравнить с кратчайшим возможным путём, у каждого лишнего шага причина (подтверждение денег, выбор) · **ветки**: ошибка · отмена · прерывание (закрыл приложение — где продолжит) · первый раз vs повторный · **выход**: где оказался и понимает ли, что получилось.
- **Главная задача — «было → стало»**: было N шагов (текущий продукт заказчика; нет — лучший конкурент из `niche.md`) → стало M. M > N → объяснить, что пользователь получает за лишний шаг; нет объяснения → переделать. Число идёт в Case и проверяется `critic-wireframe`.
- Флоу вскрыл недостающий экран или состояние → «Вопросы / находки» с предложенным решением.

